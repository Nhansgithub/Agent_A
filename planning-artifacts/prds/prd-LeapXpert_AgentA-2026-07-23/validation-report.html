PRD-to-User-Document Automation Agent Flow — Validation Report

_bmad-output/planning-artifacts/prds/prd-LeapXpert_AgentA-2026-07-23/prd.md
Fair

This is a well-shaped, substantive chain-top build spec: it carries a clear thesis (automate the drafting/revision labor of user docs while humans keep judgment via the tools they already use), honest and load-bearing non-goals (§5.2/§5.3), product-specific NFRs with real thresholds (§7), and a genuinely locked deployment story (§15). It is the right shape for a headless automation service where Jira and Confluence are the entire interface, and its procedural spine (roughly 12 of 15 FRs) is testable and will feed architecture and stories cleanly.

It grades Fair because the dimensions the stakes make unforgiving both bend. Done-ness is thin: the product's core autonomous judgments ship with no test oracle — the PRD classifier (FR-03 "genuinely a finalized PRD") and the "truly blocked" clarification heuristic (FR-08) are unfalsifiable, and the primary output (the UserDoc) has no stated acceptance mechanism. And the human-gate mechanism that is the product's whole point specifies only the happy "Done" transition, leaving rejection, abandonment, and indefinite stalls silently unhandled with no timeouts.

The adversarial pass sharpened the picture rather than shifting it, and surfaced concrete build-biters the rubric only implied: an idempotency-vs-rename-re-trigger contradiction (NFR-04 ↔ EH-04); a self-ingestion loop where publishing moves the finished doc into the very folder the webhook watches (FR-15 ↔ FR-01); a "PM who created the page" identity that contradicts "PM fixed in config"; and unacknowledged egress of confidential unreleased-PRD content to LangSmith. Several excerpt artifacts (missing §§6.3–6.6, a dangling "§Phase 5/6" reference, an undefined "SSG") show the adoption from PRD_Agent_Flow.md was not fully reconciled.

Decision-readiness

adequate

The PRD makes and states its decisions rather than burying them. The deployment target is explicitly locked (§15.1, header). §14 is a genuine architectural-decisions appendix that names trade-offs with what was given up — e.g. "Flow, not a single agent … the trade-off is that the state contract must be explicit and idempotent (owned by us, not a framework)," and "Multi-tenant single service … Container-per-tenant remains a fallback." The licensing decision (MIT LangGraph core only) is concrete and reasoned (NFR-10, §14). The Open Questions (§13) are genuinely open — build-time verifications paired with a Current assumption, not rhetorical.

What keeps this from strong: a few decisions a chain-top spec could pin are punted wholesale to "build time" (§13 Q1/Q2), and one cost-relevant decision is left un-adjudicated — FR-11's "no cap until PASS" on an otherwise cost-obsessed demo.

medium

No-cap redraft loop is an un-adjudicated cost decision

§6.1 FR-11; §3
FR-11 sets "repeats with no cap until PASS" with no round or cost ceiling and no metric tracking cumulative spend, on a demo whose entire framing is cost/latency-conscious.
Fix: state the decision explicitly — either "unbounded by design, cost accepted" or add a soft round cap / cost budget surfaced via the review_round counter and LangSmith.

§13 Q1/Q2
Exact Jira transition path to Done and folder-vs-parent model both shape the ticket-manager and publisher agents, yet are deferred wholesale.

Substance over theater

strong

Content is earned, not furniture. No persona theater — §4 Actors & Roles is functional and every role drives real FRs. No innovation/differentiation theater — none invented to fill a template. Strategic coherence

adequate

The PRD has a real thesis and the features serve one arc: detect finalized PRD → author draft → human-gated review loop → Head-of-Product publish gate → publish/export. Scope kind is coherent (problem-solving; RAG/SSG/parallelism deferred as seams). Most success metrics validate the thesis (human control: "100% of runs gated"; modifiability: "adding a 2nd project via config").

The coherence gap is measurement. There are no counter-metrics despite Success Metrics existing (§3), and the headline metric — a usable user doc — never defines "usable." The demo can score its top metric (1 successful full run) while emitting a hollow or wrong document, because nothing measures output quality and no guardrail metric is named.

medium

No counter-metrics and an undefined "usable" success bar

§3
The top goal can be met by a single happy-path run regardless of output quality; nothing guards against a hollow success.
Fix: add at least one counter-metric (e.g. classifier false-positive/negative on a small labeled set, or "PM required ≤ N revision rounds") and define what "usable" means for the demo.

Done-ness clarity

thin

The procedural spine is genuinely testable — roughly 12 of 15 FRs have verifiable consequences (FR-01 route by config; FR-02 title regex; FR-06 page+ticket created and assigned; FR-07 comment contains the four required elements; FR-12/13/14 transition-driven; FR-15 lock/move/export/mark-complete), and the DoD (§12) sharpens many into a checklist. That is real credit.

But this is the dimension story creation leans on hardest, and the product's value-producing autonomous judgments have no test oracle. FR-03 asks the classifier to confirm a page is "genuinely a finalized PRD" with no examples, accuracy target, or verification path, even though this gate decides whether the flow starts. FR-08 fires when the agent is "truly blocked … not for trivial assumptions" — untestable as stated. FR-05's UserDoc is the primary output, yet its acceptance is never declared (human PASS is the implicit but unstated oracle). And EH-02 resumes "from the last good checkpoint" without defining "step" or "checkpoint" granularity — FR-15's four sub-actions could double-apply on re-run absent stated idempotency.

high

Core autonomous judgments have no acceptance criteria or test oracle

§6.1 FR-03, FR-08
"genuinely a finalized PRD" and "truly blocked" are unfalsifiable; FR-03 gates flow entry with real false-positive/false-negative cost, and downstream stories/QA have nothing to verify against.
Fix: give the classifier a concrete decision rubric + a small labeled fixture set (accept/reject examples) and a demo accuracy expectation; give FR-08 a bounded, enumerated trigger definition.
medium

UserDoc acceptance mechanism unstated

§6.1 FR-05
The primary output's "done" is never defined; human PASS is the implicit oracle but is not declared as such, leaving FR-05's own done-ness ambiguous.
Fix: state explicitly that FR-05's acceptance is "a self-critiqued draft is produced and posted; content quality is accepted solely via the PM PASS gate (FR-12)."
medium

Resume checkpoint/step granularity undefined; multi-action step double-apply risk

§8 EH-02; §6.1 FR-15; §10
"re-run the failed step from the last good checkpoint" is unspecified, and FR-15's four sub-actions (lock, move, export, mark complete) could double-apply on re-run.
Fix: define what a checkpoint is (recommend per-stage from §9's stage list) and require each FR-15 sub-action to be individually idempotent/skippable-if-done.

Scope honesty

adequate

Omissions are largely explicit and do real work. §5.2 Out of Scope and §5.3 Future Considerations (with "leave seams") are clear and prevent gold-plating; §3 restates the non-goals; §13 surfaces assumptions in table form. Open-items density (6 build-time verifications) is appropriate for demo stakes.

The gap: §8 explicitly sets out to cover edges (title mismatch, rename re-trigger, concurrency, late feedback after Done, ambiguous PRD, loop-gating) yet is silent on the two most obvious human-gate edges. Both gates are specified only for the happy Done transition (FR-12, FR-14); non-Done terminal transitions (Rejected / Won't Do / Duplicate), reassignment, and "human never acts" are undefined, and there are no timeouts/SLAs anywhere — so a run can stall indefinitely. Because §8 covers lesser edges, this reads as oversight, not a declared decision. (Note: this dimension is graded adequate per its overall honesty, but it carries the high finding below.)

high

Only the happy "Done" transition is handled at both human gates; rejection, abandonment, and stalls silently unhandled

§6.1 FR-12/FR-14; §8
Non-Done terminal transitions have no defined behavior and there are no timeouts/SLAs, so the flow can deadlock; §8 covers lesser edges but not these, so the omission reads as an oversight rather than a decision.
Fix: add EH cases for non-Done gate transitions and a stall/timeout escalation to the admin, or explicitly declare "only the Done transition is handled; other transitions and stalls are out of demo scope."

Shape fit

strong

The PRD matches its product type well. It is a capability/technical spec — Actors & Roles, SHALL-form Functional Requirements, cross-cutting NFRs, Error Handling/Edge/Resume, Data/State, Config Registry, DoD, Deployment — exactly right for a headless multi-agent service where Jira/Confluence are the interface. Neither over-formalized (no forced UJs, no persona theater) nor under-formalized. SMs are operational (1 full run, 100% gated), appropriate for an internal automation tool. The §12 DoD acts as an acceptance checklist that partially compensates for thin per-FR criteria — a good shape choice. §9 correctly labels its implementation guidance "guidance, not prescription." No material findings; minor: some implementation detail lives inline rather than in an addendum.md, acceptable for an adopted chain-top build spec.

Adversarial review

review-adversarial-general.md

A cynical pass assuming the spec hides problems. It sharpened rather than shifted the rubric's picture, but surfaced several concrete build-biters and internal contradictions the rubric only implied. Voice preserved; not softened. The adversarial reviewer's own severities are shown; the synthesis reconciled a couple downward (e.g. the no-cap loop, which is human-gated and cannot autonomously run away).

high

You specified the gate opening, not the gate saying "no"

§6.1 FR-12/FR-14; §8
The whole product is human gates, yet FR-12/FR-14 only wait for a transition to Done. What happens when the Head of Product moves the ticket to "Rejected"? Nothing is written. You wrote an entire §8 and handled "late feedback after Done" but not "the human said NO" — that is not an edge case, it is the second-most-likely outcome of a review gate.
Fix: define behavior for every non-Done terminal transition, or declare it out of scope in §8.
high

No timeouts anywhere, in a product whose pitch is "documentation stops lagging"

§8; §6.1 FR-08/FR-12/FR-14
Every gate is "wait for human" with zero escalation. The PM goes on vacation and the run parks in awaiting_review forever. You built a system to fix "documentation lags because it depends on a human's availability" and then made every step depend on a human's availability with no backstop.
Fix: add a stall timeout that escalates to the admin (reuse the EH-01 error-comment channel).
high

FR-03 asks an LLM to confirm "genuinely a finalized PRD" and gives it nothing to decide with

§6.1 FR-03
No definition, no examples, no accuracy bar, no test oracle — and this gate decides whether the entire flow fires. A false positive drafts a public doc from half-baked notes; a false negative pesters a PM about a correct document. "Genuinely" carries the whole feature and is unfalsifiable.
Fix: concrete decision rubric + labeled accept/reject fixtures + a demo accuracy expectation.
high

"No cap until PASS" versus "no runaway loops" — pick one

§6.1 FR-11 vs §7 NFR-09
You locked a $6/mo box, demanded LangSmith cost tracing, wrote NFR-09 "no runaway loops," then removed the only cap that matters. A fussy PM drives unbounded Claude spend across unbounded rounds and nothing measures it. NFR-09's parenthetical pointedly covers only the clarification/structure loops, not the redraft loop. (Synthesis note: reconciled to medium — the redraft loop needs a PM comment each round, so it cannot spin autonomously; the real defect is the absence of a round/cost ceiling or metric.)
Fix: add a soft round/cost ceiling or explicitly accept unbounded cost as a decision.
medium

Idempotency and the rename re-trigger are in direct tension, waved at not solved

§7 NFR-04 vs §8 EH-04
NFR-04 "dedupe by entity id"; EH-04 requires the same page id to re-enter the flow after rename. So the dedupe key cannot be the entity id (or the rename never reprocesses), but if it is the event id a genuine duplicate delivery double-processes. EH-04 asserts idempotency "must ensure" no duplicate processing without saying how the two coexist.
Fix: specify the dedupe key (event id + a monotonic content/version marker) so deliberate reprocessing-on-update survives dedupe.
medium

Publishing drops the finished doc into the folder you are watching — self-ingestion

§6.1 FR-15 vs FR-01/FR-02a
FR-15 moves the final UserDoc to "the same folder as the source PRD," which FR-01 watches for page-created. The UserDoc title is not final_PRD_..., so FR-02 routes it to FR-02a — opening a rename-request ticket nagging the PM about the document you just published. Every successful publish can spawn a spurious task.
Fix: exclude the agent's own published pages from detection (tag/label or path guard), or publish to a folder outside the watched set.
medium

"PM who created the page" contradicts "PM fixed in config"

§6.1 FR-02a vs §4; §13 Q4
§4 says the PM is "Fixed in config"; FR-02a assigns the rename task to "the PM who created the page" (scraped from the Confluence creator field per §13 Q4). If an engineer or the Head of Product creates the page, the task goes to the wrong person — and you are assuming a Confluence account id maps cleanly to a Jira-assignable account, a classic Atlassian footgun.
Fix: route rename tasks to the config PM by default; use the creator only as a CC, and specify the identity-mapping source.
medium

LangSmith is a "Must" and it egresses confidential unreleased-product plans to a third-party SaaS

§7 NFR-01
100% LLM-call tracing means PRDs and derived docs for unreleased features leave to an external vendor. Not one word about data governance, redaction, retention, or whether it is even permitted.
Fix: add a data-governance note (allowed data classes, retention, redaction) or gate tracing content behind a policy switch.

Fix: guard the transition (skip if already Done; resolve the legal transition path at runtime).
